# 카풀 운영 방식 설계 (v1)

작성 2026-10-24. 근거는 [market-research-2026-10.md](market-research-2026-10.md)의 출처 번호 [S#]를 따른다.

## 원칙

- **단톡방 안에서 쓰인다.** 카카오톡·LINE 공유 링크로 일정, 교대 요청, 기록을 보낸다. 채팅을 대체하지 않는다. 가장 큰 가치는 간사의 관리 부담을 덜어 주는 것이다.
- **빠지기와 교대가 가장 중요하다.** 크루가 깨지는 1순위 원인은 불규칙한 일정이다(54-60%)[S57].

1. 매칭하지 말고 운영한다. 모르는 사람을 실시간으로 이어 주는 방식은 실패했다. FHWA Santa Barbara 시범사업에서 앱 다운로드 755건 중 두 번 이상 이용한 사람은 31명이었다[S11]. 이미 아는 사람끼리 만든 고정 크루가 기본 단위다.
2. 전날 정한다. 출퇴근하는 사람은 실시간 매칭보다 전날 확정하는 쪽을 선호한다. 매일 짝을 다시 짜면 이미 맞춰진 파트너 관계가 깨진다[S24].
3. 돈보다 공정이 먼저다. 한국에서는 기름값을 나누는 것도 유상 운송에 해당한다[S1][S2]. 그래서 기본값은 돈이 오가지 않는 공정 순번이다.
4. 앱이 먼저 연결을 만들어 준다. 후보 목록만 주면 60%가 아무에게도 연락하지 않는다[S16 계열, Commuter Computer 1980]. 앱이 크루 제안을 직접 보낸다.
5. 크루가 사라지는 것을 앱이 먼저 알아챈다. 크루는 멤버의 이사나 시간 변경으로 끝나는데, 재매칭을 요청하는 사람은 25%뿐이다[S16].

## 객체 모델

```
Group (회사·학교·동호회·학부모 모임)
 ├─ policy: 국가/지역 → 지도 제공자, 언어, 비용 정책 프리셋
 ├─ members (role: owner/admin/member, 이메일 도메인 인증 선택)
 ├─ Crew (2-6명 고정, captain 1, backup driver ≥1)
 │   ├─ WeeklyTemplate (요일별 출발/복귀, 픽업 지점)
 │   ├─ Exceptions (결석, 혼자 운전, 교대 요청)
 │   ├─ Trip (date, leg, driver, riders, status, checkin)
 │   └─ Ledger (멤버별 공정 점수, 선택: 비용 항목)
 └─ EventBoard (1회성 이벤트 카풀 보드)
```

## 흐름

| 단계 | 사용자 행동 | 앱 동작 | 근거 |
|---|---|---|---|
| 1. 그룹 만들기 | 운영자가 이름, 유형, 국가를 고른다 | 국가에 따라 지도 제공자, 언어, 비용 정책을 자동으로 정한다(KR: 출퇴근 시간대 제한, JP: 실비만, 기타: 실비 분담) | [S1][S50][S49] |
| 2. 초대 | 링크, QR, 코드를 공유한다(카카오톡/LINE) | 이메일 도메인이 맞으면 자동 승인한다. 가입 없이 웹에서 보기만 할 수도 있다 | [S33 커뮤니티 도메인 검증], Quick Ride |
| 3. 가입 | Google, 카카오, 이메일 링크로 로그인한다 | 카카오톡 인앱 브라우저에서 열리면 외부 브라우저로 넘긴다 | [S42] |
| 4. 프로필 | 대략적인 출발 지역, 평소 요일과 시간(필수), 운전 여부, 좌석 수 | 정확한 주소는 다른 멤버에게 보여 주지 않는다 | [S11] 일정을 가입 때 필수로 받자 일정 생성률이 50% 미만에서 약 100%로 올랐다 |
| 5. 크루 구성 | 제안을 수락한다 | 방향과 시간이 겹치는 사람끼리 크루를 제안하고, 전원이 수락하면 활성화한다. 킥오프 체크리스트(픽업 지점, 대기 한도 10분 등)를 함께 보낸다 | FHWA 크루 구성 가이드, GT 대학 허가제 |
| 6. 주간 일정 | 결석을 표시한다(마감은 전날 21시, 크루별로 조정 가능) | 템플릿으로 주간 일정을 만든다. 운전자는 출석자 중 Fagin-Williams 점수가 가장 낮은 사람으로 자동 배정한다 | [S13][S14][S24] |
| 7. 교대 | "이번엔 못 해요"를 누른다 | 크루 전체에 '운전자 필요' 알림을 보낸다. 다음으로 점수가 낮은 사람이 수락하면 장부가 자동으로 보정된다 | GoKid 패턴 |
| 8. 당일 | 알림을 받는다(전날 저녁, 출발 15분 전) | 운전자가 '운행 완료'를 원탭으로 누른다. 탑승자 명단은 미리 채워져 있다 | 밴풀 일일 기록부 관행 |
| 9. 기록 | 없음 | 운행 기록, 크루 월간 리포트, 그룹 대시보드(참여율, 운행 수, 절감 km·CO2)를 만들고 CSV로 내보낸다 | Liftshare, 프랑스 증빙 등급 [S27] |
| 10. 이탈 감지 | 없음 | 2주 연속 출석이 줄면 captain에게 알리고 대체 멤버를 제안한다. 크루는 삭제하지 않고 일시정지한다 | [S16] |

## 공정 순번 (Fagin-Williams)

- 탑승자가 k명인 날: 운전자 점수 +(k-1)/k, 탑승자 각자 -1/k
- 다음 운전자: 출석자 중 점수가 가장 낮은 사람. 동점이면 가장 오래전에 운전한 사람
- 결석한 날은 점수에 영향이 없다. 순서를 바꿔 운전해도 장부가 스스로 보정된다
- 코드 검증 결과(1000일, 3-6명, 출석률 60-100%): 최대 불공정도 1.12회 이하. 결석을 건너뛰는 단순 순번은 최대 11회까지 벌어진다

## 비용 정책 프리셋

| 프리셋 | 지역 | 동작 |
|---|---|---|
| `kr-rotation` | 한국 | 돈이 오가지 않는 교대 운전만 지원한다. 금액 기능은 두지 않는다. 반박 검토 결과에 따르면 교대 운전이 곧 비용 분담이고, 금액 기능과 운전자 배정을 함께 두면 알선 위험이 있다[S1][S4] |
| `free-only` | 동호회, 이벤트, 주말 | 운전 크레딧만 쓴다 |
| `actual-cost` | JP, FR, DE, UK, US 등 | 실비(연료 ÷ 탑승 인원, 운전자 포함)를 사용자가 직접 정한다. 앱은 금액을 강제하지 않고 정산은 앱 밖에서 한다 |

한국 규칙: v1에는 금액 계산 기능이 없다. 회비에 운행 비용을 넣는 방식도 유상이다[S4].

## 기본값으로 하지 않는 것

- 실시간 GPS 추적: 위치정보법 신고 대상이고[S5], 운영 도구의 핵심 기능도 아니다. 필요하면 '도착 예정 공유'를 일회성으로만 제공한다.
- 앱 내 결제: 결제 기능이 운송 중개로 해석될 위험이 있고, 앱 스토어 정책 이슈도 생긴다[S43].
- 포인트와 리더보드를 핵심 동기로 쓰는 것: 지속 효과가 약하다[S12]. 대신 크루 단위 챌린지와 단체의 주차 우대 연동을 쓴다.
